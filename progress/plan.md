# quorin-benchmarks — Phase-1 Plan

> Companion to `quorin` (https://pypi.org/project/quorin/). This repo is a
> third-party-style comparative benchmark suite: head-to-head measurements of
> Quorin vs. the realistic alternatives a team picking a feature-store today
> would consider. Linux/WSL2 only (matches Quorin's scope). Methodology
> mirrors Quorin's [ADR-015 §6 + §11](https://github.com/MahinAshraful/Quorin/blob/main/docs/adr/015-benchmark-methodology.md).

---

## 1. Why this repo exists (and why it's separate)

Quorin's in-repo `benchmarks/` suite is a **regression detector**: it
benches Quorin against Quorin (warm vs. cold, pooled vs. unpooled, batch
vs. single, schema-N vs. schema-M). It's tier-1/tier-2 gated, run on
every push, and lives in the same repo as the code under test.

That suite **does not** answer the question every reader of the README
arrives with: *"how does this compare to Redis HGETALL? to a Python
dict? to Apache Arrow? to Feast?"* Putting comparative benches inside
the Quorin repo was rejected for two reasons:

- **Mixing scopes.** A regression suite must remain stable across
  releases of Quorin alone; a comparative suite must add and drop
  competitors without touching Quorin's CI matrix.
- **Source independence.** Numbers published by the library author in
  the library's own repository carry weaker evidentiary weight than
  the same numbers published in a separately-maintained repository
  with documented methodology. The ADR-015 reporting discipline is
  preserved by the separation.

So `quorin-benchmarks` is its own repo. Quorin is consumed via
`pip install quorin` from PyPI; we don't import from a sibling
checkout. The Quorin commit under test is pinned in `pyproject.toml`.

---

## 2. The questions Phase 1 must answer

For each question, the phrasing is "Quorin vs. X across Y workload."
Phase 1 is intentionally narrow:

| # | Question | Stores compared | Workload |
|---|---|---|---|
| Q1 | What is single-entity warm read p99 across stores? | Quorin / Redis HGETALL / Python dict / stdlib shm | `single_read warm` |
| Q2 | What is single-entity cold read p99 across stores? | same | `single_read cold` (4×L3 clobber) |
| Q3 | How does each store scale on batch reads (N=10..10000)? | same | `batch_read` |
| Q4 | At 50k RPS mixed 95/5, where does each store's p99 fall? | same | `mixed_workload` |

Phase 2 adds: multi-process concurrent (1/4/16/64 workers), cold start,
sustained-throughput soak, crash recovery, schema upgrade, capacity
boundary. Phase 2 also adds Plasma / Feast / lmdb / Memcached.

Phase 3 widens the hardware matrix. Phase 4 wraps end-to-end ML serving
stacks. Phase 5 layers operational benchmarks. Out of scope for Phase 1.

## 3. Methodology contract (mirrors Quorin ADR-015)

Phase 1 ships with the following methodology rigor — non-negotiable:

1. **Fresh subprocess per data point.** `runners/fresh_subprocess.py`
   spawns `N=20` brand-new Python interpreters per (scenario, store)
   combination. Aggregates report `median(p99)`, `stddev(p99)`, and
   `max_of_max`. Never `max-of-max-of-max` — that's a sample of a
   sample.

2. **Identical input data across stores.** A single `_data.py` builds
   the entity-id list and the row payloads **once** (deterministic
   seed). All stores' setup phases load from the same in-memory
   structure. We don't re-pack 1000 floats per store.

3. **Numba prewarm BEFORE the timed loop.** Quorin's adapter calls
   `quorin.assembly.prewarm()` in setup. The ~200 ms first-call LLVM
   init is paid in setup, not measurement. Other stores have no
   equivalent; they get the same setup-vs-measurement split for
   parity.

4. **Cold-cache via 4×L3 clobber array, not numactl.** Detect L3 from
   `/sys/devices/system/cpu/cpu0/cache/index3/size`; fall back to
   16 MiB with a `WARN` log if missing. Never fall back to L2 (ADR-015
   §4 — silently measures L2-cold). Traverse the array between calls
   to evict cache lines for cold reads.

5. **Hardware metadata captured per run.** `runners/hardware_collector.py`
   writes a `_hardware.json` next to the result JSONs containing:
   kernel version, CPU model, `/proc/cpuinfo`, available memory, /dev/shm
   size, Python version, pinned dep versions. Required field on every
   result JSON.

6. **Pinned everything.** Python 3.12 (matches Quorin's `.python-version`).
   Quorin pinned to `==0.1.0` in `pyproject.toml`. All deps pinned with
   `==`. A reproducible Docker image (`docker/Dockerfile`) is the
   reference environment.

7. **JSONs committed to `results/<hardware>/<scenario>/<store>.json`.**
   Each commit's CI job overwrites only the `ubuntu-latest` slice; other
   hardware classes are landed by hand from the operator's machine.
   Markdown summaries are generated by `analysis/render_table.py` from
   the JSONs, never edited by hand.

8. **Visible progress.** Every scenario × store × run prints a single
   stderr line `→ scenario=X store=Y run=07/20 p99=... us`. A 30-min
   run is not a black box.

9. **Single-process pytest-benchmark numbers are NOT a Phase-1
   deliverable.** They land in result JSON only as supplementary data
   marked `regression_only=True`. Headline numbers come from the
   N=20 fresh-subprocess aggregator. Same rule Quorin's ADR-015 §6
   adopted.

10. **Honest disclosure.** The README explicitly states what each
    venue measures and does not measure. Bare-metal extrapolation is
    acceptable as a footnote, never as the reported number.

## 5. The Store Protocol

`stores/_base.py` defines:

```python
from typing import Protocol
import numpy as np

class Store(Protocol):
    """Adapter contract: one implementation per backend.

    Lifecycle:
      __init__(*, capacity: int, schema_name: str) — connect / create.
      populate(rows: list[tuple[str, dict]]) — one-shot bulk load.
      read(entity_id: str) -> np.ndarray — single-entity hot path.
      read_batch(entity_ids: list[str]) -> np.ndarray — batch hot path.
      write(entity_id: str, row: dict) — single-entity write.
      close() — release all resources, no /dev/shm leaks, no Redis keys.

    All adapters return float32 1-D arrays for read() in the SAME
    declaration order as the canonical schema in _schema.py. Adapters
    that store typed dicts (Redis HGETALL) must reconstruct the same
    array shape so scenario code is store-agnostic.
    """

    name: str  # human-readable, lowercase-snake (e.g. "quorin", "redis_hgetall")

    def __init__(self, *, capacity: int, schema_name: str) -> None: ...
    def populate(self, rows: list[tuple[str, dict]]) -> None: ...
    def read(self, entity_id: str) -> np.ndarray: ...
    def read_batch(self, entity_ids: list[str]) -> np.ndarray: ...
    def write(self, entity_id: str, row: dict) -> None: ...
    def close(self) -> None: ...
```

Schema kept tiny + canonical: `_schema.py` exports `CANONICAL_SCHEMA`
(4 fields: `feat_a` float32 scalar, `feat_b` int64 scalar, `feat_c`
float32 (16,), `feat_d` float64 scalar). Total element count = 19,
output dtype float32. Future scenarios can construct alternate schemas;
Phase 1 uses just this one to keep the cross-store comparison apples-
to-apples.

## 6. Per-store implementation notes

### 6.1 `quorin_store.py`
- Use `quorin.schema.FeatureSchema`, `quorin.shm.SegmentRegistry`,
  `quorin.layout.pack_row + insert`, `quorin.assembly.assemble +
  prewarm`, `quorin._internal.posix_shm.unlink`.
- `__init__` calls `prewarm()` synchronously.
- `populate()` uses per-row `pack_row + insert` (not the bulk Numba
  `insert_many` kernel). Reason: keep parity with what other stores
  do — they all loop. Bulk is a Quorin-internal optimization that's
  out of scope for "comparative single-write throughput" (a Phase-2
  scenario). Loop keeps the 4 stores honest at the boundary.
- `read()` is `quorin.assembly.assemble(seg, eid)`.
- `read_batch()` is a Python-loop call to `assemble` (we are NOT
  using Quorin's `assemble_batch` Numba kernel for Phase 1 because
  none of the other stores have a vectorized batch path either; using
  the Quorin kernel here would compare different shapes of code).
- `close()` calls `registry.close + posix_shm.unlink`. No watchdog
  reliance — bench is in-process.

### 6.2 `redis_hgetall.py`
- Single `redis.Redis` client; HSET on populate (one HSET per entity
  with all fields msgpack-packed as a single `blob` field — matches
  what production code does). Read is HGET `blob`, msgpack-unpack into
  the canonical float32 array.
- We deliberately don't HGETALL field-by-field; that's slower than
  blob-and-unpack and isn't what production code actually does.
  Documented in the adapter docstring.
- `read_batch()` uses pipelined HGET. Batched RTT is the only honest
  comparison.

### 6.3 `inprocess_dict.py`
- `dict[str, np.ndarray]`. Latency floor — what every other store has
  to beat. No serialization, no IPC, no locking.
- This is the "what would a single-process notebook get?" baseline. If
  Quorin beats it on warm reads we have a Numba bug; if it loses by
  more than a factor of 2 we have evidence Quorin's overhead is
  bounded.

### 6.4 `stdlib_shm.py`
- `multiprocessing.shared_memory.SharedMemory` + `np.frombuffer` views
  + a Python dict mapping `entity_id -> row_index`. The dict is
  process-local — to keep the in-process bench honest, this adapter
  also runs in one process.
- This is the manual-shared-memory baseline — the path a developer
  would take using only the Python standard library. Quorin's
  [ADR-001](https://github.com/MahinAshraful/Quorin/blob/main/docs/adr/001-posix-shm-over-multiprocessing-shared-memory.md)
  documents why this approach is unsafe in production. Phase 1
  measures raw layout speed only; the cross-process correctness gap
  surfaces in Phase 2.
- The cross-process correctness gap is a *Phase-2* scenario
  (`multiprocess_concurrent`), not a Phase-1 latency comparison.

## 7. Per-scenario implementation notes

Each scenario module exports a `run(store: Store, *, n_iters: int,
warm: bool) -> dict[str, float]` function. The fresh-subprocess
runner imports the scenario, instantiates the store, calls
`store.populate(rows)`, runs the timed loop, returns latency stats
(p50/p95/p99/p999/max/min/median, n_samples).

### 7.1 `single_read.py`
- Populate `capacity=10000` entities with deterministic-random data.
- Pick `n_iters` random entity_ids (deterministic seed).
- Hot loop: `store.read(eid)`, capture `time.perf_counter_ns()` deltas.
- `warm=True`: no clobber. `warm=False`: 4×L3 clobber array traversal
  between every call.
- Return per-percentile dict.

### 7.2 `batch_read.py`
- Populate as above. Parametrize over `batch_size in {10, 100, 1000,
  10000}` (caller picks one per invocation).
- Hot loop: `store.read_batch(batch)` once per measurement; the
  measurement is per-batch wall-clock, divided by batch_size for
  per-key amortized latency. Both reported.

### 7.3 `mixed_workload.py`
- Populate. 50k RPS target (ratelimited by `time.sleep` between calls,
  best-effort — actual achieved RPS reported in the JSON).
- 95% reads, 5% writes (chosen via deterministic prng). Track
  read-only and write-only latency distributions separately so a slow
  write path doesn't pollute read-side numbers.
- Run for `duration_seconds` (default 30 in CI, 60 in operator runs).
  Phase 2 lifts to 30 min for sustained-throughput soak; Phase 1 keeps
  it short to fit in CI minutes.

## 8. The runner

`runners/fresh_subprocess.py` mirrors Quorin's `benchmarks/runs/repeat.py`.
It:

1. Takes a YAML spec: `scenario`, `store`, `n_iters`, `warm`, `n_runs`.
2. Spawns `n_runs` subprocesses; each runs
   `python -m runners.fresh_subprocess --inner-mode <spec.json>`.
3. Each subprocess: imports scenario + store, runs the scenario once,
   prints a one-line per-run JSON to stdout. Parent collects.
4. Aggregates: `median(p50)`, `median(p99)`, `stddev(p99)`,
   `max_of_max`. Writes to `results/<hw>/<scenario>/<store>.json`.

`runners/matrix_runner.py` is the high-level entry. It iterates over
all (scenario, store) tuples for a given phase, calls
`fresh_subprocess.py` for each, and writes a `_matrix.json` summary.
This is what `make benchmark` invokes.

`runners/hardware_collector.py` runs once at the start of any
`matrix_runner` invocation and dumps `_hardware.json` to the result
directory. Pure stdlib + `/proc/cpuinfo`.

Runtime budget for `make benchmark` on Phase 1, ubuntu-latest:
- 4 stores × 3 scenarios × 2 modes (warm/cold) × 20 fresh runs × ~5 s
  per run ≈ **40 minutes**. Tight for CI free tier; cut to N=5 in CI
  and keep N=20 for operator runs. Documented in
  `benchmark_phase1.yml`.

The "headline" comparison table in `README.md` is generated by

hand-edited so the README remains a flat file (no SaaS pipeline).

## 11. Honest-disclosure checklist (in README)

The `README.md` includes a section "What this measures (and does not)":

- We measure **single-machine** read/write latency with all stores
  warm. Phase 1 does NOT cross network boundaries beyond Redis on
  localhost, does NOT touch disk for any store, does NOT model
  durability.
- Quorin's number is the assemble + lookup hot path; Redis HGETALL's
  number is the round-trip to a localhost Redis. Different shapes of
  guarantees.
- Cold-cache numbers are CPU-cache-cold, not page-cache-cold. Tmpfs
  shared memory is RAM-resident.
- Numbers are venue-specific; bare-metal multipliers are mentioned
  as a footnote, never as a primary claim.

## 14. Post-build review — issues found + fixed

After the initial build, a second-pass review surfaced five real
issues. All were applied in-place; the following are the load-bearing
notes future readers should know about:

### 14.1 Quorin adapter: never mutate `_schema_class.__name__` post-hoc
**Was:** `self._schema_class.__name__ = schema_name` (and `__qualname__`)
after `quorin_schema_class()` returned. Quorin derives segment names
and control-plane keys from the schema's name; renaming after
construction risks splitting the bookkeeping between the compiled
form and Quorin's internal hashes. The smoke run accidentally worked
at small scale, but it's not an invariant we control.
**Fix:** drop the rename. The canonical name in `_schema.py`
("BENCH_SCHEMA") is the single source of truth; the `schema_name`
kwarg from the Store protocol is informational only and explicitly
ignored (`# noqa: ARG002`).

### 14.2 stdlib_shm: zero-copy read via `unpack_from`
**Was:** `bytes(self._buf[offset:offset+_ROW_BYTES])` (one memcpy)
followed by `_STRUCT.unpack(blob_bytes)` (decode of that bytes).
Two unnecessary copies per read at ~250 ns each on WSL2.
**Fix:** `_STRUCT.unpack_from(self._shm.buf, offset)` reads directly
off the SharedMemory buffer protocol, no copy. **Measured impact:
~25% p99 reduction (3.90 µs → 2.98 µs WSL2)**. This makes the
manual-shared-memory baseline a fairer comparison: a competent
manual implementation would not pay these copies either.

### 14.3 mixed_workload: drop `time.sleep`-based rate limiting
**Was:** `time.sleep(next_emit - now)` to cap RPS at a configured
target. Linux `time.sleep` has ~50-200 µs minimum granularity. At
any target RPS above ~5k the inter-call sleep budget (< 200 µs) is
unreachable, so sub-microsecond stores ran at approximately 1/200th
of the configured rate; millisecond-class stores never reached the
sleep at all. The reported "target RPS" was therefore a configured
input that no store actually attained, while two very different
per-call latencies could produce nominally identical RPS numbers.
**Fix:** the rate cap is removed. The loop runs at full speed for
`duration_seconds` and reports `achieved_rps` directly. The matrix
subdir was renamed `mixed_50k_rps` → `mixed_95r_5w` to reflect the
workload shape rather than a target.

### 14.4 single_read / batch_read: warmup pass
**Was:** the timed loop started cold — the first ~50 reads paid
first-touch page faults, branch-prediction misses, and (for
Redis) connection-pool init costs that don't represent steady-state.
**Fix:** discard `warmup_iters` (default 100 for single_read,
10 for batch_read) before the timed loop. For cold-cache mode the
warmup also traverses the clobber array per call, so the warmup
itself is cold-cache (otherwise we'd warm the working set during
warmup and measure something between warm and cold). The discarded
count is reported in the result JSON as
`warmup_iters_discarded` for traceability.

### 14.5 Aggregator: preserve constant non-numeric fields
**Was:** `_is_numeric` filter dropped strings; the per-run
`mode: "warm"` / `mode: "cold"` tag never made it to the aggregate
JSON. A reader had to parse `extra_args` to recover it.
**Fix:** if every run agrees on a non-numeric field's value, pass
it through unchanged into `aggregate`. If runs disagree, drop it
but record `_<field>_inconsistent: true` so the drop is visible.

### 14.6 Deferred (documented, not fixed)

* **`inprocess_dict` measurement is harness-dominated.**
  `perf_counter_ns()` × 2 per call ≈ 60 ns of pure clock overhead.
  At 0.10 µs p50 the timing harness is ~60% of the reading. The
  honest framing is "in-process dict reads are too fast to time
  per-call accurately with our harness; the floor is the harness
  itself, not the dict." Other stores share the same harness so
  comparisons are still fair. Not a fix — any change breaks parity
  with the other Phase-1 stores.

* **CI auto-commits to `main` every push.** The `benchmark_phase1.yml`
  workflow commits result JSONs back to main on every push. Spams
  the git log with mostly-noise commits. Phase-2 follow-up:
  land them on a `results-history` branch, or rely on the workflow
  artifact alone and only land via `workflow_dispatch`.

* **Multiple-of-2 stores in matrix run sequentially per scenario,
  not per store.** The current loop iterates
  `for combo: for store:` so a Redis populate is followed by a
  Quorin populate within the same scenario subdir. Acceptable for
  Phase 1; if cache effects between adjacent runs ever matter,
  flip to `for store: for combo:` and add explicit Redis FLUSHALL
  between store transitions.

* **`np.random` instead of `random.Random` in `_data.py`.** At
  10k entities × 16-dim embeddings, the Python-level RNG takes
  ~50 ms (small share of setup). At 1M entities it'd be ~5 s.
  Defer to Phase 2 if/when capacities scale up; until then,
  reproducibility-via-Python-seed is the simpler contract.
